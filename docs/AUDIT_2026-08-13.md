# EXECUTIVE VERDICT

**This is an unusually well-built prototype with an unusually honest self-assessment, and it is not a product. It is roughly 18 months of good architectural thinking and about 6 weeks from being safely runnable by one paying customer.**

The contracts layer, the error model, the degradation ladder and the documentation are genuinely top-decile work — better than most Series-B codebases I have reviewed. The problem is not quality of thought. The problem is that **a large fraction of the Stage 21–30 capability was built as a library and never wired into the request path**, and the build report describes the library rather than the running system.

Three findings would each independently block a funding diligence:

1. **The grounding gate does not apply to the LLM director.** `check_spec` is called only from `RuleBasedVisualDirector._ground` (`director.py:223`). `LlmVisualDirector.direct()` validates the model's payload into a `VisualPlan` and returns it with **no grounding check whatsoever**. The gate is present exactly where hallucination is impossible (deterministic rules over extracted quantities) and absent exactly where it is certain (a language model inventing chart values). The moment `VTV_TEXT_GENERATION_API_KEY` is set — the production configuration — the anti-hallucination guarantee silently ceases to exist. The build report's Stage 24 claim is, in the production configuration, **false**.

2. **`POST /internal/sweep` is unauthenticated and destroys data across all tenants.** `app.py:1180` has no `guard()` call. It enumerates expired projects globally, deletes them, and sweeps storage. Any unauthenticated party who can reach the API can trigger cross-tenant deletion.

3. **The durable queue has zero production callers.** `create_app` instantiates `InProcessJobQueue` (`app.py:170`). `DurableJobQueue` appears only in its own module and its own test file. Every Stage 27/28 claim — crash recovery, exactly-once claiming, dead letters, restart survival — describes 1,035 lines of code that no request ever touches. Meanwhile the actual queue holds jobs as asyncio tasks with an in-memory idempotency dict, and renders run **synchronously inside the API event loop**.

The pattern is consistent and worth naming plainly: **this repository has excellent components and an under-built composition root.** `wiring.py` and `api/app.py` are where the system is actually assembled, and they are the least rigorous files in the codebase.

**Overall production readiness: 31/100.** Not because the engineering is bad — because the thing that runs is not the thing that was described.

## 3. WHAT IS NOT PRODUCTION-READY

**The composition root.** `api/app.py` (1,323 lines) and `wiring.py` are where every architectural guarantee is either realised or lost, and this is where the guarantees are lost.

Concretely, the running system:

- executes CPU-bound video rendering inside the API event loop
- keeps all render results in a process-local unbounded dict
- rate-limits per process
- reserves quota per process
- performs 3+ synchronous SQLite connections per request, one of which scans all tenants
- serves an unauthenticated destructive endpoint
- returns other tenants' projects when `organisation_id` is null
- never applies the Visual Bible it builds
- never grounds LLM-produced visual plans

## 4. CRITICAL BLOCKERS

### C1 — Grounding bypass via the LLM director · RED · **NOT PROVEN SAFE; PROVEN UNSAFE BY INSPECTION**

`director.py:74` imports `check_spec`; the only call site is `_ground()` inside `RuleBasedVisualDirector` (`director.py:223, 546`). `LlmVisualDirector.direct()` builds a `GenerationRequest`, parses the response with `VisualPlan.model_validate(payload)`, calls `_require_every_scene`, and returns. No `Evidence`, no `check_spec`.

`wiring.py` makes `LlmVisualDirector` the director whenever a text credential is present, with the rules director as *fallback*. So in production the ungrounded path is primary.

Impact: a model can emit a `ChartSpec` with fabricated values and it will be rendered into a customer-facing video with no check. This directly contradicts `docs/GROUNDING.md` and `BUILD_REPORT.md`.

**The gate must move.** It belongs in the composer or the plan-validation boundary, not inside one director implementation — that is precisely the "caller-enforced invariant" failure mode the brief asked me to hunt for.

### C2 — Unauthenticated cross-tenant destructive endpoint · RED

`app.py:1180`, `Route("/internal/sweep", sweep, methods=["POST"])`. No `guard()`. Deletes expired projects globally and sweeps object storage. The docstring acknowledges it should not be an endpoint in production; nothing enforces that.

### C3 — Tenant isolation fails open for null-organisation projects · RED

```python
owner = getattr(project, "organisation_id", None)
if owner is not None and not principal.owns(owner):
    return None
return project                       # app.py:364-367
```

`organisation_id` is `Id | None`. Any project created outside `create_project` — `Pipeline.run()` with a default `Project()`, the demo path, `visualise_text`, evaluation runs, or any row written before this column existed — has `organisation_id = None` and is therefore **readable and editable by every authenticated tenant**. The check should be `if not principal.owns(owner)` with `None` failing closed, and the column should be non-nullable.

The passing test suite does not catch this because every project in `test_api_security.py` is created through `create_project`, which always sets the field.

### C4 — Renders execute in the API event loop · RED

`InProcessJobQueue.enqueue` creates an asyncio task; `run_pipeline` awaits `Pipeline.run`, whose renderer runs a synchronous frame loop (`ffmpeg_renderer.py:216-228`) writing to a `Popen` pipe. There is no `to_thread`, no executor, no separate worker process.

A single 30-second render blocks **every** request on that process — health checks, authentication, SSE streams — for the duration. Two concurrent renders serialise. This is not a scaling concern; it is an availability failure at n=2 users.

### C5 — The durable queue is dead code · RED

Zero production references. All Stage 27/28 guarantees are untestable in production because the code is not on the path. The system's actual delivery semantics are: **at-most-once, in-process, non-durable**, with idempotency held in a dict that dies with the process.

To use the correct technical term as requested: the running system provides **at-most-once delivery with no durability**. The unused `DurableJobQueue` would provide **at-least-once delivery with idempotent claiming** (not exactly-once — its `_execute` can crash after handler completion and before `_settle`, causing a re-run; the effects must be idempotent, and settling usage is *not* idempotent across that window unless the `idempotency_key` covers it, which it does only for the render record, not for the reservation release).

### C6 — Password authentication cannot function · RED (as a deployment property)

`Directory.verify_password` raises `NotImplementedError`. `pyproject.toml` declares no `argon2-cffi` or `bcrypt` in any extra. The dependency profile therefore **cannot authenticate a human user by password at all**. Fail-closed is the right *behaviour*; shipping without the dependency in any extra means the only working auth is API keys, and there is no SSO integration. **There is no way for an end user to log in.** That is a product blocker, not a security nicety.

## 5. HIGH RISKS

**H1 — Rate limiter is process-local.** `RateLimiter._buckets` is a dict. N replicas ⇒ N× every limit, including `LOGIN_LIMIT`. Credential stuffing scales with your own autoscaling.

**H2 — Quota reservations are process-local.** `_reserved()` reads `self._reservations` (`usage.py:347, 239`), never the `usage_reservations` table it also writes. Two replicas cannot see each other's holds. The concurrency guarantee in `docs/BILLING.md` and the passing test both hold only within one process.

**H3 — `suspended_ids()` on every request.** `app.py:345` reads every organisation row and JSON-parses each one, per request. O(tenants) per request, synchronous, in the event loop. At 10,000 tenants this is the whole system.

**H4 — Synchronous SQLite inside async handlers, everywhere.** ~25 call sites. Every one blocks the loop. `Directory._connect()` opens a new connection and re-issues PRAGMAs per call — no pooling.

**H5 — `state.results` is unbounded and non-shared.** Video, storyboard, captions and thumbnails are served only from this dict. Restart ⇒ every completed video becomes unreachable (the MP4 survives in storage; the API cannot find it). Second replica ⇒ 404 depending on which pod you hit. Memory grows without bound.

**H6 — Reservation leak on crash.** `expire_reservations()` exists and **is never called by anything**. No scheduler, no sweep, no startup hook. A crashed render permanently consumes quota in the DB table (and the in-memory dict simply vanishes, silently freeing it — the two stores disagree after any restart).

**H7 — Ingestion bypasses upload inspection.** `IngestionService.ingest()` calls `ParserRegistry.parse` directly. `archive_is_safe` is never invoked from the ingestion layer — only from `inspect_upload` on the HTTP route. DOCX/PPTX/XLSX parsers open zips directly. Any non-HTTP caller (worker, CLI, future batch import) has no bomb protection.

**H8 — `security/paths.py` has zero production callers.** `safe_join`, `safe_storage_key`, `tenant_key`, `safe_filename` are exported from `security/__init__.py`, fully tested, and used nowhere. Storage keys are built with f-strings (`f"projects/{timeline.project_id}/renders/..."`, `ffmpeg_renderer.py:245`). The path-traversal defence is decorative.

**H9 — No parser timeouts.** `_guard` bounds bytes and `MAX_BLOCKS` bounds output, but nothing bounds *time* or *peak memory*. A crafted PDF that makes pypdf spin has no wall-clock bound, and it runs in the event loop.

**H10 — `authenticate()` does DB work before the rate-limit check.** `directory.authenticate(credential)` (a SQLite read) runs first; `limiter.require` is called only in the `except` branch (`app.py:309-311`). An attacker gets unlimited-rate database lookups; the limiter only fires after the work is done.

## 6. MEDIUM RISKS

- **M1 — `development_principal()` races.** Concurrent first requests both find no org and both call `create_organisation`; the unique slug turns the loser into a `PolicyViolation` → 403 on a legitimate request. It also picks `members[0]`, which is arbitrary.
- **M2 — Audit writes are synchronous and unbatched**, one connection per entry, in the request path.
- **M3 — SSE endpoint polls a dict every 0.5s for up to 15 minutes**, holding a worker slot per connected browser, in a single-process server.
- **M4 — `X-Forwarded-For` trusted unconditionally** (`_client_ip`). Documented as requiring a proxy; nothing enforces it. Spoofable ⇒ the login limiter is bypassable by header.
- **M5 — No pagination anywhere.** `/v1/audit` caps at 500, `keys_for` is unbounded, `list_projects` takes a limit with no cursor.
- **M6 — No API versioning strategy** beyond the `/v1` prefix; no deprecation policy, no response-schema contract tests.
- **M7 — Renders are not idempotent at the artifact level.** `idempotency_key=f"pipeline:{project_id}"` prevents double-enqueue while the key is in memory; after restart the same upload re-renders and re-charges (the usage key includes `render_job_id`, which is fresh each time).
- **M8 — `revise_scene` mutates `result.visual_plan` in place** on a shared in-memory object with no locking, then persists. Two concurrent edits race.
- **M9 — CORS `allow_origins` from settings; no CSRF protection.** Acceptable for a pure bearer-token API; becomes a hole the moment a cookie session is added.

## 7. ARCHITECTURAL DEBT

The dominant debt is a single structural pattern: **guarantees implemented as helper functions the caller must remember to call.**

| Guarantee | Where it lives | Where it is enforced | Gap |
| --- | --- | --- | --- |
| Grounding | `pipeline/grounding.py` | one director | LLM director bypasses |
| Tenant scoping | `Principal.owns` | each route, manually | null-org fails open |
| Path safety | `security/paths.py` | nowhere | dead code |
| Upload safety | `security/uploads.py` | HTTP route only | ingestion bypasses |
| Quota | `billing/usage.py` | two routes, manually | any new route forgets |
| Durability | `queue/durable.py` | nowhere | dead code |

Every one of these should be enforced at a chokepoint the caller cannot route around: a repository that refuses an unscoped query, a storage provider that only accepts tenant-prefixed keys, a plan-validation step every director's output passes through, a job submission API that is the only way to start work.

Secondary debt:

- `api/app.py` is 1,323 lines with all handlers as closures over `create_app` locals. Untestable in isolation, impossible to review incrementally, and the reason guards are applied by copy-paste.
- `PipelineResult` is a god-object carrying eleven optional documents plus flags. Its optionality is why `_persist` silently omits `visual_bible` — nothing forces exhaustiveness.
- No migration framework. `CREATE TABLE IF NOT EXISTS` only. `organisation_id` was added to an existing table with no backfill path — which is exactly how C3's null rows arise.

## 9. SCALABILITY RISKS

Structural blockers to horizontal scaling, in the order they bite:

| Users | What breaks | Why |
| --- | --- | --- |
| **2 concurrent** | Latency collapses | Render blocks the event loop (C4) |
| **~10** | Availability | One render ⇒ all requests stall 25s+ |
| **2 replicas** | Correctness | Rate limits ×2, quotas unbounded, `state.results` splits, idempotency splits |
| **~1k tenants** | Throughput | `suspended_ids()` full scan per request (H3) |
| **~10k projects** | Memory | `state.results` unbounded (H5) |
| **Any restart** | Data availability | All results lost; jobs lost |

The system as wired **cannot run two replicas correctly**. That is the headline scalability fact. Not "does not scale well" — *cannot be replicated at all* without correctness loss in rate limiting, quotas, result serving and job idempotency.

Beyond that: SQLite with a new connection per call and no pooling; local filesystem storage with `path_for` used directly by the media route (no S3 path exercised); no read replicas; no caching layer; no CDN for artifacts.

## 10. PRODUCT CORRECTNESS RISKS

**Where the pipeline can succeed while the product fails:**

1. **Mute video reported as success.** The API returns `202`, the job completes, `render_job.status = READY`, `succeeded == True`. The `narration.has_speech = False` signal reaches the caller only via `GET /v1/projects/{id}` if they read the optional `narration` key, and via a `notes` array in the 202. **`PipelineResult.succeeded` does not consider it.** Verdict on the brief's specific question: this is **ORANGE, not GREEN** — degradation is disclosed in two places but is not part of the success predicate, so any client checking `status == "ready"` ships a silent video to an end user believing it succeeded.

2. **Every scene can degrade to typography and still be "success".** The fallback ladder is sound, but there is no quality floor and no aggregate degradation threshold. A project where 100% of scenes fell to the last rung renders and reports success.

3. **Ungrounded charts in the LLM path** (C1) — the pipeline succeeds while producing fabricated evidence. This is the worst product-correctness failure available to this system.

4. **Visual Bible produces no consistency.** It is built (`orchestrator.py:312`), reviewed, stored on the result — and **never read by composition, animation or rendering**. Recurring entities are *not* visually consistent. The feature does not exist in the output.

5. **No word-level caption timing** for real STT, and for documents all timings are synthetic and uniformly rescaled — captions will drift against any real synthesised speech beyond the segment level.

6. **Document→video quality is unvalidated.** No evaluation case covers the document path end-to-end. The corpus is text/voice only.

## 12. DATA / PRIVACY RISKS

- **No encryption at rest.** `LocalStorageProvider.put` writes plaintext bytes. `docs/SECURITY.md` claims "server-side encryption at rest on every bucket" — **NOT IMPLEMENTED** in the only storage adapter that runs.
- **Deletion is not proven complete.** `delete_project` removes rows; storage objects are swept separately by age, not by project. A deleted project's MP4 and audio persist until the age sweep. GDPR erasure is therefore **not** satisfied. `docs/SECURITY.md` claims "Deletion is real. Not a tombstone." — **stronger than the code**.
- **Retention is per-plan in data but unenforced** — `max_retention_days` is never read by any sweep.
- **Consent flags exist and default correctly.** Good. No export path filters on them yet because no export exists.
- **Audit log retains IP and user-agent** with a 400-day security retention; defensible, but there is no DSAR path to produce or purge a subject's audit entries.
- **Raw voice** is `EPHEMERAL` by contract; the sweep that enforces it is the unauthenticated endpoint (C2), not a scheduled job.

## 13. DEPLOYMENT RISKS

There is **no deployment artifact at all**: no Dockerfile, no compose file, no Kubernetes manifests, no entrypoint beyond `uvicorn`, no health/readiness distinction (`/health` does provider probes — unsuitable as a liveness probe), no graceful shutdown (in-flight asyncio renders are killed silently), no config validation at boot.

Things that would break immediately under orchestration:

- local disk for storage (`var/storage`) — requires RWX volume, defeats replication
- SQLite files for directory, audit, usage, projects — **cannot be shared across pods safely**
- process memory for results, rate limits, reservations, job state
- `WEB_ROOT` computed from `__file__` — breaks in a wheel install
- `Path("./var/vtv.db")` fallback — CWD-dependent

**Verdict: the system is a single-binary, single-node application.** Nothing about that is stated in `PRODUCTION_READINESS.md`'s deployment section, which is the most significant omission in that otherwise-honest document.

## 19. WHAT SHOULD BE REBUILT RATHER THAN PATCHED

1. **`api/app.py`.** 1,323 lines of closures. Rebuild as routers with dependency injection and a middleware that applies auth/tenant/limit uniformly, so a new route cannot forget. This single change eliminates C2, C3 and most of §7.
2. **The job layer.** Not "swap the queue" — the API currently *is* the worker. Split into `vtv-api` and `vtv-worker` binaries with the queue as the only boundary.
3. **`InProcessJobQueue`.** Keep for tests; remove from wiring entirely so it cannot be selected in production.
4. **`PipelineResult`.** Replace the optional-everything god-object with an explicit stage-result union, so persistence exhaustiveness is checkable (the reason `visual_bible` was silently dropped).
5. **Storage key construction.** One function, enforced by the port's type signature.

Everything else — contracts, errors, parsers, animation, security primitives — should be kept as-is. They are good.

# THE 10 HIGHEST-LEVERAGE CHANGES

1. **Make grounding a property of `VisualPlan`, not of one director.** One chokepoint; removes the worst product risk permanently.
2. **Split `vtv-api` from `vtv-worker` and wire `DurableJobQueue`.** Converts four RED items into GREEN and unlocks every scaling conversation.
3. **Rebuild routing with middleware-applied auth/tenant/limit/audit.** Makes "a new route forgot the guard" structurally impossible; kills C2 and C3 as a class.
4. **Make `organisation_id` non-nullable and push scoping into the repository** (Postgres RLS as the backstop). Isolation by architecture, not discipline.
5. **Move rate limits, quota reservations and job state to Postgres/Redis.** The single change that makes replication correct.
6. **Serve artifacts from storage + repository, never from process memory.** Removes the restart cliff and the memory leak together.
7. **Enforce tenant-prefixed storage keys in the port's signature.** Turns dead `paths.py` into a real boundary.
8. **Sandbox document parsing** (subprocess, rlimits, wall clock) and call `inspect_upload` inside `IngestionService`.
9. **Ship Dockerfile + migrations + lockfile with hashes.** Three artifacts that move deployment readiness from 8 to ~50.
10. **Add a success predicate that includes degradation.** `succeeded` must mean "narrated, grounded, and rendered" — otherwise the honesty in the docstrings never reaches the customer's client.

## Closing assessment

The instinct that produced this codebase — contracts first, honesty in docstrings, refuse rather than fake, record every degradation — is the right instinct, and it is rarer than good code. The `STATUS:` lines, the "Missing, and named" table and the refusal to hash passwords badly are things I almost never see in an acquisition target.

But the review's central finding is uncomfortable and should not be softened: **the build report describes the library, and the library is not the system.** Grounding, durability, consistency and path safety were each built to a high standard and then not connected. The gap between `docs/` and `wiring.py` is the entire distance between this repository and a company.

That gap is closable in roughly six focused weeks, because the components are sound and the seams already exist. Nothing here needs to be thrown away. But nothing here should be sold yet, and no claim in `BUILD_REPORT.md` about Stages 23, 24, 27 or 28 should be repeated to an investor, a customer or an auditor until the wiring matches the prose.

**NOT PROVEN FROM STATIC INSPECTION:** lxml external-entity behaviour inside python-docx/python-pptx; actual render determinism byte-for-byte; real memory ceilings under adversarial documents; whether `mypy --strict` and the 500 tests pass at this commit (not executed, per instruction).
